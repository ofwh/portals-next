# API 规范

本文规定自有业务接口的服务分层、service 约定、响应与错误处理。

## 服务分层

业务接口遵循 `api -> services -> repositories -> db` 调用方向，必须包含 api 和 services 层；涉及数据库读写时，通过 repositories 访问 db。

- **api**：解析请求、调用 service、构造响应。不处理业务规则或逐字段校验，不直接访问 repositories 或 db。
- **services**：负责业务规则与参数校验。不写 SQL，数据库读写交给 repository。
- **repositories**：只负责数据库操作，不做业务判断，只被 services 调用。
- **db**：Drizzle 实例与 schema；schema 组织遵守[数据库规范](../AGENTS.md#数据库)规范。

## Service 约定

- 方法名使用简洁、明确的单词，例如 `list`, `update`, `detail`, `remove` 等。
- 创建与更新统一使用 `update`。未提供主键等记录标识时创建；提供时更新指定记录，记录不存在则返回业务错误。
- 更新支持部分字段：仅修改请求中提供的字段，未提供的保持原值；可空字段通过 `null` 清空。创建时校验必填字段，主键及系统维护字段不允许通过业务参数修改。
- 分页查询使用 `list`，参数统一为 `page`（页码）和 `size`（每页条数），均须为正整数，页码从 `1` 开始。
- 方法分别具名导出，并通过默认导出对象聚合；调用方通过该对象调用方法。

## 请求与响应

- API 层通过 `lib/api` 的 `readParams` 或 `readForm` 解析请求，解析失败返回统一错误响应；解析结果不代替 service 的运行时校验。
- 自有业务接口使用 `BaseResponse<T>`，HTTP 状态统一为 `200`，以响应体 `code` 判断业务成败。
- 成功响应通过 `okResponse` 构造，`code` 为 `0`，`data` 为业务结果，`message` 为 `OK`，不返回 `error`。
- 失败响应通过 `errorResponse` 构造，`code` 为数值错误码，`data` 为 `null`，`error` 为 `{ code, message }`；其中 `error.code` 为稳定的命名空间错误标识，`message` 与 `error.message` 相同。
- 服务端统一入口使用 `lib/api/server`，语言选择遵循[国际化规范](i18n.md)；公共响应与错误工具不得依赖鉴权或数据库模块。
- 业务 API 的请求鉴权统一在根目录 `proxy.ts` 配置，不在 `lib/api/server` 或 service 层执行。
- 未知异常转换为公共内部错误，响应中不得暴露原始异常、数据库信息、凭据或调用栈。

## 错误归属

- 公共错误定义在 `lib/api/codes.ts`，文案保存在 `lib/api/messages/{locale}.json`，只表达与具体业务无关的失败原因。
- 业务错误按业务定义在 `lib/errors/`，分别导出 `codes` 和 `messages`，通过 `lib/errors/index.ts` 聚合。
- service 使用 `appError(code, params?)` 抛出明确错误，由 API 统一转换为响应；不得使用 HTTP 状态码代替错误码，不得在调用处拼接或覆盖错误文案。
- 参数格式、类型、取值范围及不支持的字段统一使用 `common.INVALID_PARAMS`，不按校验细节拆分错误码。
- 业务约束失败使用所属业务错误，不能折叠为公共参数错误或公共请求失败。数据库唯一约束冲突由 service 转换为对应业务错误。

## 编号与文案

- 公共错误使用四位数 `1000`–`9999`；优先复用语义一致的已有错误，新增时从已使用的最大编号递增分配。
- 业务错误使用七位数，由两位业务码、两位模块码和三位错误编号组成；数值为 `业务码 * 100000 + 模块码 * 1000 + 错误编号`。
- 当前应用业务码使用 `10`–`49`，从 `10` 开始；模块码使用 `01`–`99`，从 `01` 开始；错误编号使用 `000`–`999`，从 `000` 开始。
- 同一业务保持业务码不变；新增业务、模块或错误在所属范围内按已使用或预留的最大编号递增分配，不回填空号。超出范围时停止分配。
- 数值错误码全局唯一；错误标识采用 `<命名空间>.<错误名>`，在命名空间内唯一；不同语言的错误键必须一致。
- 每个错误在每种语言下对应一个固定模板，动态信息仅通过命名参数插值；新增错误须同步维护所有支持语言的文案。
- 已使用或预留的编号不得重排、复用或转移归属；废弃错误保留原编号。

### 业务码占用登记

分配前核对本表及错误定义源码；发现未登记或归属冲突时，先补齐登记或解决冲突。分配或预留业务码后立即更新本表；尚无错误定义时标注“待定义”。停用业务保留登记。具体模块码、错误编号和文案以源码为准，不在文档重复列举。

| 业务码 | 所属业务 | 错误定义位置                  |
| ------ | -------- | ----------------------------- |
| `10`   | 路由管理 | `lib/errors/routes.ts`        |
| `11`   | 路由别名 | `lib/errors/shortcuts.ts`     |
| `12`   | 标签管理 | `lib/errors/tags.ts`          |
| `13`   | 工作流   | `lib/errors/workflow.ts`      |
| `14`   | 订阅管理 | `lib/errors/subscriptions.ts` |

## 协议边界

第三方协议入口及实际路由转发、重定向、缓存和静态内容交付可保留协议要求的方法、状态码、响应体与响应头；这些例外仅限对应协议适配层，不扩展为普通管理接口规则。Better Auth 认证入口保留其原生协议响应。SSE 流的协议边界见[工作流运行时接入约束](workflow-technical-design.md#61-运行时接入边界)。
