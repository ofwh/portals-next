# 工作流节点开发

开始前读取仓库根目录 [AGENTS.md](../../../AGENTS.md)，再读取 [工作流技术方案](../../../docs/workflow-technical-design.md) 中与本次修改相关的章节。接口及视图开发分别沿用其中链接的规范，类型遵守 [AGENTS 类型规范](../../../AGENTS.md#类型)，语言遵守[国际化规范](../../../docs/i18n.md)；不在技能中另行定义通用规则。

## 确定边界

从用户要求确定节点所属组、输入输出语义、配置草稿和执行行为。先检查已有节点与核心能力，仅在无法从需求或源码确认业务语义时询问用户。不附带生成页面或无关节点。

读取 `lib/workflow/nodes/types.ts` 与 `lib/workflow/nodes/core/` 的实际契约；目录、泛型、解析职责、端口规则和前后端边界以技术方案为准。涉及配置与视图时读取方案第 4 节；涉及专用类型时读取第 2、4.1 节。

## 实现与接入

节点内服务模块放入 `services/`，工具模块放入 `utils/`。实现保留在具名模块中，两类目录的 `index.ts` 仅统一导出，外部通过目录入口引用。

按技术方案第 3、7 节组织节点并完成组内导出。配置草稿的结构判断与执行时严格校验应区分：向视图注册中心提供的 `isConfig` 必须接受合法的未完成草稿，不得用执行配置校验拒绝用户正在编辑的内容。

查看 `lib/workflow/nodes/index.ts` 和 `lib/workflow/nodes/client.ts`，分别接入后端注册与前端视图注册。专用类型先于使用它的节点注册；后端与前端需要类型匹配时分别加载同一安全类型定义。按需使用注册中心的组接口生成清单，不另建静态清单或在页面增加节点专用分支。

节点实例的版本来自注册清单，不使用流程版本代替。修改已保存配置的结构时，按技术方案的快照与节点版本边界处理；不能通过更改版本标记让旧配置绕过校验。

仅在业务需要时扩展共享能力。新增业务错误沿用 [API 规范](../../../docs/api.md) 的归属及编号规则。

## 检查与交付

按仓库现有命令执行类型、lint 和相关文件格式检查，并审查前端入口是否引入 executor 或服务端依赖。测试相关工作遵守 AGENTS.md，不自行扩大范围。

交付说明只包含节点行为、接入位置、检查结果及实际限制。文档只记录不能从源码直接获取的约束，通过链接引用现有规范。
